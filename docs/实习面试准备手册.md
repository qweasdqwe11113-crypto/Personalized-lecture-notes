## 一、项目定位与面试介绍

### Q01【P0】这个项目究竟解决什么问题？

**业务问题：** 教师备课时需要把课程资料、学生薄弱点和授课要求组合起来，生成可以进一步修改的讲义。直接聊天虽然能生成文字，但材料来源、实际输入、历史版本和修改依据容易丢失。

**当前项目：** 一个本地教学工作空间。教师管理课程材料和学生画像，选取资料、图片识读记录及本次教学要求，生成讲义，再进行来源核查、人工修订和导出。讲义还可以派生课件、题目等内容。

**价值表述：** 把“生成一段文字”变成有资料依据、输入记录和人工复核环节的工作流程。是否节省教师时间，需要真实使用与评测，不能只凭功能数量断言。

**可能追问：** 谁是使用者？使用频率是什么？为什么现成聊天产品不够？你是否观察过真实教师备课？如果没有，明确这是原型阶段，用户价值还需要访谈验证。

### Q02【P0】用一分钟介绍项目，怎么说？

参考表达，个人职责部分必须按事实填写：

> 这是一个面向教师备课的 AI 教学工作空间，使用 Flask、PostgreSQL 和原生 JavaScript。主流程是把课程资料、学生画像和教学要求组织成上下文，再调用语言模型生成讲义。材料可以按知识点用 SQL 精确取用，也可以使用向量检索；图片先由视觉模型识读成文字，再作为生成证据。
>
> 工程上，系统把生成请求和上下文在提交时固定下来，后台队列执行长耗时调用，保存成功和失败记录，支持原输入重试、来源核查和人工修订。我主要负责的是【真实负责范围】，其中深入解决过【具体问题】。当前是本机单进程原型，效果和并发能力的边界也有明确记录。

**两分钟版再补：** 一个最有技术含量的问题、你的修改、验证证据。不要按菜单顺序介绍所有页面。

### Q03【P0】这个项目和“套模型接口”有什么区别？

模型调用确实是其中一环，但工程工作还包括：

1. 资料导入、正文提取和图片识读，建立课程关联。
2. 在正确知识点范围内取材料，控制上下文长度。
3. 管理学生证据，区分长期画像与本次备注。
4. 冻结实际请求，记录检索来源、模型用量与失败信息。
5. 处理排队、超时、取消、重试和进程中断。
6. 保留原稿、修订和审核记录。

**回答关键：** 选其中一项讲到代码和失败场景。功能存在不等于你掌握了实现，面试官会继续追问。

### Q04【P0】你用的是 AI Agent 吗？训练过模型吗？

核心讲义链路更接近**确定性业务编排下的 RAG 应用**：程序决定检索、上下文整理、模型调用和保存步骤。不能因为调用了多个模型，就称为模型自主决策的多智能体系统。

当前核心链路以调用已有模型服务为主。没有训练或微调证据时，应直接说没有训练模型，把工作重点放在数据组织、应用实现与评测。

相关概念：

| 概念 | 核心区别 | 项目对应 |
| --- | --- | --- |
| Prompt Engineering | 修改输入指令与示例 | 有不同任务的提示模板 |
| RAG | 检索外部资料后再生成 | 有 SQL 材料取用及向量检索模式 |
| Fine-tuning | 用训练数据更新模型参数 | 不应宣称已完成 |
| Agent | 模型参与工具和步骤决策，通常有循环与状态 | 核心链路不需要用这个词包装 |

### Q05【P0】现在有哪些功能不能夸大？

| 可以依据代码说明 | 不能直接据此声称 |
| --- | --- |
| 有向量检索实现和后端选择 | 已使用 HNSW 或已经支持百万文档 |

| 固定请求正文和 SHA-256 | 同一输入必然得到相同输出，或具备防篡改认证 |

| 生成失败可按原输入重试 | 外部模型只执行一次或重试结果必然相同 |
| 有图片识读链路 | 建好了统一图文向量库、实现了图像端到端联合训练 |

这些边界不是项目不能展示的理由。能够解释边界，本身就是工程理解的体现。

## 二、架构与完整业务链路

### Q06【P0】你能画出系统架构吗？

可以先用下面这张文字图，不依赖绘图工具：

```text
浏览器：HTML / CSS / 原生 JavaScript
               │ HTTP JSON API、任务状态轮询
               ▼
Flask app.py：参数校验、业务装配、上下文构建
  ├─ 课程与学生：catalog.py / profiles.py
  ├─ 上传与识图：uploads.py / vision.py / assets.py
  ├─ 检索：retrieval.py / embed.py
  ├─ 输入准备：lecture_policy.py / prompts.py / teaching.py
  ├─ 后台任务：jobs.py → execute_job → qwen.py
  └─ 审核与派生：reviews.py / sections.py / presentations.py
               │
    PostgreSQL 教学主库 + SQLite 上传与阅卷库
               │
    外部语言模型 / 视觉模型 / Embedding 服务
```

**要能解释：** Web 请求、后台线程和模型服务不是同一件事；PostgreSQL 与 SQLite 分别保存哪些数据；模型地址和模型名称来自配置，源码默认值不证明当前线上运行的模型版本。

### Q07【P0】用户点击“生成讲义”后发生什么？

核心路径：

1. 前端提交学生、课程、目标、检索模式、教学要求和所选图片解析编号。
2. 后端校验字段、课程归属和输入长度。
3. `get_context()` 读取资料、学生状态及诊断证据；向量模式还会准备索引并执行检索。
4. `finalize_context()` 生成讲解安排，控制输入预算。
5. `prepare_request()` 生成实际模型请求正文、版本和摘要。
6. `JobQueue.submit()` 保存 run 与 job，提交数据库事务后放入本进程队列。
7. worker 取出任务，获得共享语言生成锁，进入执行函数。
8. 模型发送前记录 attempt，`call_qwen()` 发送已经准备好的正文。
9. 收到响应后检查协议、截断、空内容和引用编号等。
10. 保存讲义和成功运行记录；失败则保存分类错误。前端通过任务 ID 轮询。

**重要细节：** 提交接口本身可能涉及索引和 Embedding 请求，不是所有耗时操作都天然已经移到后台。面试官问“提交为什么也会慢”时，可以从这里分析。

### Q08【P0】上传文件后，它就进入 RAG 了吗？

不是。当前需要分清几个状态：

- 原文件和提取正文进入上传存储。
- 教师把上传正文显式关联到课程副本及知识点，写入 PostgreSQL `materials`。
- SQL 模式可按知识点直接使用材料，不需要 Embedding。
- 向量模式对材料分块并建立或更新向量，再执行查询。
- 图片通过所选识读记录进入生成证据，是另一条通道。

**为什么要这样做？** “系统里存在这份资料”与“这份资料适合本次课程”是不同判断。显式关联能控制资料范围，但也增加用户操作，需要从真实使用反馈评估。

### Q09【P1】为什么图片先转成文字，再交给语言模型？

当前讲义链路采用分阶段处理：VLM 识读图片，教师选择解析记录，语言模型根据解析文字生成讲义。

优点是中间结果可查看、可复用、可追溯，也能让语言生成继续使用统一文字上下文。缺点是图片中的空间、图表和细节可能在识读时丢失；后续语言模型无法重新观察原图纠正错误。

因此要保留原图身份、解析版本和不确定性。重要数值、坐标和公式应能回看原图核对。

### Q10【P1】为什么项目拆成这么多模块？

按职责拆分有助于把检索、网络传输、队列、持久化和审核独立理解与测试。例如替换 Embedding 客户端，不应要求同步重写讲义修订逻辑。

当前 `app.py` 仍承担较多装配和业务流程，前端也有全局状态及加载顺序依赖。可改进方向是明确服务层和数据接口，逐步降低耦合。不要为了面试把整个项目重写一遍；先找实际维护问题，再做局部重构。

## 三、RAG 与向量检索

### Q11【P0】什么是 RAG？为什么你的项目需要它？

RAG 是 Retrieval-Augmented Generation，即检索增强生成。先从外部知识中找相关内容，再把它放入模型输入，让模型据此回答或生成。

在本项目中，课程材料是外部依据。模型自身知识可能不符合课程范围，也不了解教师当前上传的资料。通过检索引入材料，可以更新依据并保留来源，但不能保证模型一定正确理解和使用材料。

完整链路是：**导入 → 清洗 → 建立课程关联 → 分块与索引 → 查询 → 排序选取 → 组织上下文 → 生成 → 检查与评测**。

### Q12【P0】SQL 模式和向量模式有什么区别？

| 维度 | SQL 材料取用 | 向量检索 |
| --- | --- | --- |
| 选择依据 | 已知课程与知识点关系 | 知识点范围内的语义相似度 |
| 当前实现 | 查询对应 `materials` | 分块向量排序，默认取 6 块 |
| 优点 | 确定、可解释、不调用 Embedding | 长材料较多时能选相关片段 |
| 局限 | 资料多时上下文容易膨胀 | 可能漏掉关键定义或公式条件 |
| 适用情况 | 少量、整理好的课程摘要 | 较多且表达多样的课程材料 |

默认 SQL 是合理基线。不能预先认定向量模式更先进就一定更好，应该用相同任务比较覆盖率、质量和成本。当前向量模式也不是在全库无范围地搜索，先受所选知识点约束。

### Q13【P0】Embedding 是什么？与语言生成模型有什么区别？

Embedding 把文本映射成固定维度的数值向量，使相关文本在某种距离度量下更接近。语言生成模型则根据上下文预测后续 token 并生成内容。

提供 `/chat/completions` 的服务不一定提供 `/embeddings`，同一模型名也不能直接证明支持嵌入。项目有 `QwenEmbedder`、`OllamaEmbedder` 适配；实际可用性必须通过真实接口验证。

**常见追问：为什么不能混用不同模型的向量？** 不同模型的向量空间没有统一坐标意义。即使维度相同，也不能认为相似度可比较。更换模型通常需要重建索引；还应记录模型版本、维度和预处理方式。

### Q14【P0】为什么分块？当前怎么分？

整份文档太长，可能稀释主题、增加输入成本，也不利于精确定位。太小的块又会丢失定义、公式条件和上下文。

当前 `retrieval.py` 使用确定性的文本分块：优先按换行组织内容，对仍然过长的块滑动切分。默认 `CHUNK_SIZE=500`、`CHUNK_OVERLAP=80`，这里按 Python 字符长度计算，**不是 500 token**。

重叠主要用于过长块的滑动窗口，并不是所有相邻段落都保证重叠 80 字。应按真实实现解释。

**如何调参？** 构造包含定义、推导和例题的评测集，比较不同块长与重叠的关键证据召回、生成质量和 token 成本。500/80 是当前配置，不是已经证明最优的参数。

### Q15【P0】余弦相似度怎么算？

```text
cos(a, b) = Σ(aᵢ × bᵢ) / (sqrt(Σaᵢ²) × sqrt(Σbᵢ²))
cosine_distance = 1 - cosine_similarity
```

它比较向量方向。若两个向量都已做 L2 归一化，余弦相似度等于点积。

例子：`a=(1,0)`、`b=(0.8,0.6)`，两者范数都为 1，相似度为 0.8。项目数组实现对零向量返回 0，对维度不一致抛出错误。

**注意：** 相似度 0.8 不是“80% 概率正确”。不同模型和数据集的分数分布不同，阈值要用样本校准。

### Q16【P0】你实际用了什么向量数据库？用了近似索引吗？

项目把分块保存在 PostgreSQL `material_chunks`。`select_backend()` 检查 pgvector 扩展，存在时优先选择 pgvector 路径；否则使用 `ArrayBackend`，把知识点范围内的向量读取出来，在 Python 中计算余弦并排序。

数组路径是精确扫描，不是向量索引。设候选块数为 N、维度为 D，距离计算约为 O(ND)，当前完整排序约为 O(N log N)，还要承担数据传输和 Python 对象的内存开销。

pgvector 路径使用 `<=>` 余弦距离操作符。**出现这个操作符或安装了扩展，不等于已经建立 HNSW/IVFFlat 索引。** 还要检查列类型、DDL、索引和 `EXPLAIN` 执行计划。本文没有连接运行库确认实际后端和索引，不应把代码支持描述为当前部署事实。

### Q17【P1】Top-K 为什么是 6？越大越好吗？

当前默认取 6 个分块，是实现参数。它不是 6 份完整文档，也不一定能覆盖所有知识点。

K 小可能漏证据，K 大可能增加无关内容、重复和费用。项目会把同一材料的召回块按原顺序组合，并保留材料级 `[M编号]`。

调优应同时考虑关键证据召回、重复程度、知识点覆盖和实际生成质量。如果一个知识点内容挤占了全部名额，可考虑每知识点配额、去重、多样性选择或重排；这些应作为候选改进验证。

### Q18【P1】检索 query 是怎么构建的？

`build_query()` 以教学目标为基础，有画像时补充需要支持的知识点名称。当前上下文构建还可在画像模式加入本次学生备注。

这体现了“用任务与学习需求影响检索”，但也意味着有/无画像时检索输入和召回内容都可能变化。若要单独研究画像对写作的影响，应固定检索材料；若研究端到端效果，则可允许检索变化，但要解释清楚实验变量。

### Q19【P1】文档修改或更换模型后，如何处理旧向量？

当前 `index_material()` 检查分块数量、块位置、正文 SHA-256、Embedding 模型名和来源等元信息。不匹配时重新生成分块向量。

它使用 PostgreSQL 事务级 advisory lock，按材料 ID 串行化索引替换，降低并发请求重复替换同一材料的风险。

**进一步追问：** 模型名不变但服务实际升级了怎么办？现有模型名检查不够。可增加模型修订标识和索引配置版本。当前在持锁事务中等待嵌入响应，也会增加长事务和锁等待；规模扩大后可以设计“读取版本 → 锁外计算 → 校验版本并短事务写入”。

### Q20【P1】什么是混合检索、Rerank、HNSW？

- **关键词检索/BM25：** 依靠词项匹配、词频和文档统计，对术语、编号和专有词有优势。
- **混合检索：** 合并关键词与向量候选，可采用 RRF 等方法融合排名。不同来源原始分数不能随意相加。
- **Rerank：** 对初步召回候选进行更细的相关性判断，常用 query-document 配对模型，通常增加延迟。
- **HNSW：** 近似最近邻图索引，用内存、构建成本和召回率换取查询速度。
- **IVFFlat：** 基于聚类划分候选范围的近似索引，效果与数据分布和探测参数有关。

这些是扩展知识，当前核心代码不能据此宣称已经实现。小数据规模先保留精确基线，只有测到瓶颈或质量问题时再引入复杂组件。

### Q21【P0】检索效果不好时，你先查什么？

按链路逐层查，避免一开始只改提示词：

1. 文件正文是否提取完整，公式和表格是否丢失？
2. 资料是否真正关联到当前课程与知识点？
3. 分块是否切断公式条件或例题步骤？
4. 索引是否过期，模型和维度是否匹配？
5. query 是否表达了问题，范围过滤是否过窄？
6. Top-K 中是否包含必要证据，是否重复过多？
7. 片段是否在上下文预算阶段被截取或丢弃？
8. 证据已经进入实际请求后，模型是否仍然错误使用？

**建议准备的真实案例：** 找一个检索失败输入，保存原文、块边界、候选排名、最终请求和输出，完成一次可复查的改进。

## 四、VLM、模型调用与提示词

### Q22【P0】VLM 和 OCR 的区别是什么？

OCR 侧重文字检测与识别；VLM 能结合视觉和语言解释图表、版式及图像关系。但 VLM 可能补全不存在的内容，也不保证小字、公式和坐标识别准确。

选择时看材料性质：清晰扫描文本可用 OCR，复杂图表可能需要 VLM，实际系统也可以结合两者。要用带人工真值的样本比较字符、公式、数值和结构错误，不能只凭“看起来识别得很流畅”。

本项目保存图片及识读记录，选择时建立 `[V编号]` 来源。讲义语言模型收到解析文字，不能宣称自己直接看过原图。

### Q23【P0】Token、上下文窗口、max_tokens 是什么？

- **Token：** 模型分词后的处理单位，与汉字数、英文单词数没有固定一一对应关系。
- **上下文窗口：** 一次推理可容纳的 token 范围，具体输入输出约束要看模型与服务协议。
- **max_tokens：** 请求输出上限，并不是要求生成的准确字数，也不能只靠它保证整次请求不超上下文。

项目目前用字符预算控制材料和上下文，并设置输出 token 上限。字符控制是实用近似，不能当精确 token 计数。更严格时应使用对应模型 tokenizer，并给输出和协议开销预留空间。

### Q24【P1】上下文太长怎么办？

先减少无关输入，再选择相关且完整的证据，保留原文位置与来源。项目 `lecture_policy.py` 中材料预算为 16000 字符、上下文预算为 56000 字符；超预算材料按知识点轮流选择并节选，节选保存原文范围和摘要，预算不是模型窗口的精确换算。

盲目取前 N 字会丢掉后面的重要条件；单纯让模型总结又可能引入新的错误。可比较章节切分、目标相关片段选择和分层摘要，但要检查关键证据是否保留。

**追问：长上下文模型还需要 RAG 吗？** 仍可能需要。长窗口不等于模型能稳定利用每一段，资料权限、来源定位、延迟和成本也不会自动解决。小材料则可以把整份输入作为合理基线。

### Q25【P0】temperature 低，结果就可复现吗？

不能保证。temperature 控制采样分布；降低它通常减少变化，但服务实现、模型版本和并行计算等仍可能影响输出。temperature 为 0 也不应被当作跨环境完全确定的承诺。

项目讲义请求通常设置 `temperature=0.3`。固定请求能复查“当时发了什么”，不能保证以后重发得到完全相同正文。评测需要多次重复并记录模型、参数和时间。

### Q26【P0】Prompt 怎么组织？如何管理版本？

`prompts.py` 根据课程类型选择提示文件，把课程、材料、画像和教学设置放入结构化上下文，构造 system/user 消息；再生成紧凑 JSON 正文和 SHA-256，同时记录提示与输入结构版本。

好提示应说明角色、任务、材料边界、输出结构、不确定性和引用要求。提示词是影响模型行为的方法，不是安全隔离或正确性证明。

**如何验证改 Prompt 有效？** 固定评测任务和模型，对比具体错误率、引用支持、目标覆盖、延迟和成本。不能仅凭一次输出更长或更流畅判断。

### Q27【P0】SHA-256 在这里起什么作用？

对实际发送的请求正文 UTF-8 字节计算摘要，读取和重试时重新计算，检查正文是否和保存摘要一致。

```text
准备正文 → 计算 SHA-256 → 保存正文与摘要 → 发送相同正文
```

它便于输入一致性核查，但：

- 不是加密，不能隐藏正文或学生信息。
- 不是签名，若正文和摘要都被有权限的人改掉，普通哈希检查无法证明来源可信。
- 不是模型输出确定性，也不是请求幂等键。
- JSON 字段顺序、空格等变化会影响字节摘要，所以这里保存原始正文，而不是重试时重新拼装。

### Q28【P0】为什么要分类处理模型错误？

配置错误、连不上、HTTP 错误、超时、响应 JSON 损坏、协议字段缺失、空正文、输出截断、无效引用，原因和用户操作不同。

`qwen.py` 用 `ModelError` 保存稳定错误码、阶段和安全消息。响应若 `finish_reason='length'`，按截断处理，不保存为完整成功讲义。部分内容可以用于排查，但应与完整结果区分。

排查日志要能通过 run ID 关联阶段，不直接把上游原始异常、密钥或 DSN 返回给前端。错误分类还可用于统计服务稳定性。

### Q29【P1】什么是结构化输出？如何保证 JSON 符合要求？

“请返回 JSON”只是提示，模型仍可能缺字段、类型错或输出多余文本。处理至少包含：JSON 解析、字段与类型校验、枚举与长度校验、跨字段业务校验。

项目 PPT 和出题流程对相应输出做结构和业务校验。若服务支持 JSON Schema 约束，可减少格式错误，但不能证明答案和引用正确。修复请求应有次数上限，记录原始错误和修复成本，避免无限重试。

### Q30【P0】怎样减少幻觉？引用为什么还要人审？

减少幻觉可以从材料覆盖、检索质量、指令边界、缺证据时说明不足、输出检查和人工复核共同入手。

需要区分三层：

1. **编号存在：** `[M11]` 确实出现在本次材料列表。
2. **来源支持：** 材料 M11 的内容确实支持这句话。
3. **知识正确：** 这句话本身是否正确，适用条件是否齐全。

项目自动检查主要覆盖结构、篇幅、编号和部分关键词。它可以发现不存在的编号，不能证明支持关系或任意数学推导。审核环节正是为这些边界保留人工判断。

### Q31【P1】这算多模态 RAG 吗？为什么不用 LangChain？

可以准确描述为“结合视觉识读和文本检索的教学生成流程”。图片转文字后参与生成，并不等于已经实现图文联合向量空间、图片向量召回或端到端多模态检索。

LangChain 等框架可以统一适配、编排与观测，但框架名称不是能力指标。当前链路较固定，直接实现有助于精确保存正文和控制错误路径；代价是更多协议和流程维护工作。是否引入框架，应看是否减少实际复杂度，并验证不会破坏输入追溯。

## 五、后台任务、并发与可靠性

### Q32【P0】为什么需要后台队列？

模型调用耗时长且可能失败。若浏览器一直等待同步响应，用户刷新或网络中断后很难判断任务结果，也容易重复提交。

后台方式先返回任务身份，worker 执行，前端查询状态。它改善任务管理和交互，但不会直接让模型算得更快，也不意味着请求准备阶段毫无耗时。

主队列 `JobQueue` 是单进程、单 worker、有界队列，默认容量 4，包含当前 active 和 pending。出题有独立队列，语言调用又受共享锁约束，不能把 4 当成整个系统所有任务的统一总上限。

### Q33【P0】Lock、Condition、deque 分别做什么？

- `deque` 保存待执行任务，队首取出，适合 FIFO。
- `Condition` 保护队列和 active 状态，允许 worker 在没有任务时等待、提交时通知，避免空转。
- `GENERATION_LOCK` 控制同一进程内语言生成调用的并发。

这些是不同层次的同步。队列状态检查和修改需要作为一个临界区；即使某个容器操作在特定解释器中看似原子，也不能据此认为整段多步逻辑安全。

### Q34【P0】Python 有 GIL，为什么还要锁？线程还有用吗？

GIL 不保证“检查容量 → 保存记录 → 入队”这样的复合操作原子，也不能提供业务互斥。线程仍需通过锁或条件变量协调共享状态。

模型 HTTP 调用是 I/O 等待，线程可以让服务继续处理其他请求。CPU 密集计算是否能并行，取决于解释器构建及本地库是否释放 GIL；传统 CPython 中常考虑多进程。不能简单说“Python 线程没用”，也不能说“有 GIL 就没有并发问题”。

### Q35【P0】任务状态怎样流转？

```text
queued ──→ running ──→ succeeded
  │            └────→ failed
  └──────→ cancelled

服务中断后的恢复核查：queued / running → interrupted
如果对应运行已成功，则恢复为 succeeded
```

要区分 job 和 run：job 管排队执行，run 记录固定输入、调用与结果。当前 run 不是照搬 job 的全部状态；例如创建时 run 可处于 `running`，而 job 仍为 `queued`，是否真的尝试发送还要看 `attempted_at`。

状态更新使用类似 `WHERE status='running'` 的条件，限制非法重复完成。写状态机时要问：终态能否变化？谁能更新？是否能被重复请求触发？

### Q36【P0】重启后自动继续任务吗？

不会自动重发旧模型请求。恢复逻辑核查未完成 job 的关联 run：已成功的同步为成功，其余按中断处理，需要用户核对后重试。

原因是进程退出时，远端模型可能已经执行，甚至结果已返回但本地尚未提交。数据库里的“未确认”不等于“远端没有执行”。自动重发可能重复计算和计费。

保存状态有助于恢复判断，但内存队列不会因此变成持久消息队列。还存在“数据库提交成功、内存入队前退出”的窗口，当前选择中断核查而不是保证自动继续。

### Q37【P0】重试和重新生成有什么区别？有没有幂等性？

原输入重试读取失败 run，核查摘要，复用保存的请求正文和上下文，创建新 job/run，并记录父运行。重新生成则读取当前资料、画像和设置，输入可能变化。

**要分清三件事：**

- 单个 run 的成功提交受到事务和状态条件约束，防止重复完成。
- 同一个 HTTP 提交请求重复发送，不代表已有全局幂等键去重。
- 外部模型请求是否重复执行，不由本地状态条件单独保证。

未来可对提交引入业务幂等键与唯一约束；若上游支持幂等键或 request ID 查询，再把远端结果核查纳入流程。不要宣称现在实现了 exactly-once。

### Q38【P1】为什么只能取消排队任务？

排队任务还未发往模型，可从本地队列移除并保存取消状态。模型调用一旦发出，仅关闭页面或停止本地等待，不一定能中止远端推理和计费。

运行中取消需要上游取消接口或协作机制，并定义取消与成功返回的竞争情况。当前限制为取消尚未开始的任务，是可以明确解释的能力边界。

### Q39【P1】队列满了怎么办？共享锁有什么问题？

当前容量满返回 429，停止中可返回 503。有界队列提供背压，防止无限堆积任务和不可接受的等待。

共享语言锁保护本地或共享模型容量，但吞吐受单任务服务时间限制，慢任务会拖住其他语言任务。不同队列争抢同一锁也不等于全局严格 FIFO 或公平调度；Embedding/VLM 请求不能笼统认为也受这把锁串行化。

若要改进，先测排队时间与模型时间，再考虑超时、优先级、按用户配额、模型服务允许的有限并发。没有测量前不必直接把并发数拉大。

## 六、数据库、版本与一致性

### Q40【P0】数据库里最重要的表有哪些？

| 表或表组 | 主要职责 |
| --- | --- |
| `students`、`knowledge_points` | 学生与知识点实体 |
| `student_knowledge`、`learning_evidence` | 当前掌握状态和判断依据 |
| `course_tasks`、`knowledge_aliases` | 备课副本与诊断身份映射 |
| `materials`、`material_chunks` | 原材料、分块与向量 |
| `generation_runs` | 冻结输入、调用尝试、结果和失败 |
| `generation_jobs` | 排队状态及关联 run |
| `lectures`、`lecture_revisions`、`lecture_issues` | 原稿、修订和问题记录 |
| `lecture_experiments`、`lecture_experiment_cells` | 固定对照及实验单元 |
| `quiz_jobs` | 出题任务与结果 |

SQLite 上传库保存原资料、图片和解析；阅卷另有 SQLite 库。不是所有业务都在 PostgreSQL，也不要把 PostgreSQL 图片辅助表与上传库中的实际图片通道混为一谈。

### Q41【P0】为什么既用关系字段，又保存 JSONB 快照？

稳定实体和关联适合关系字段：学生、知识点、任务身份，以及外键、唯一约束和常用筛选条件。

生成上下文、模型元数据和检查报告结构较灵活，适合用 JSONB 保存完整快照。这样修改当前画像或材料后，历史讲义仍有当时依据。

代价是快照冗余、历史结构兼容和查询复杂度增加。不能把所有数据都塞进 JSONB，频繁筛选或需要强约束的字段仍应认真建模。

### Q42【P0】事务 ACID 在项目里怎么体现？

- **原子性：** 保存讲义和标记 run 成功一起提交，不能只成功一半。
- **一致性：** 外键、唯一约束和合法状态限制维护数据库规则；业务正确性还依赖应用逻辑。
- **隔离性：** 并发读写由隔离级别和锁共同影响。
- **持久性：** 已提交数据在数据库承诺的故障与存储条件下保留，不等于已经做好备份容灾。

`save_success()` 插入讲义并条件更新 run，主生成流程在同一事务里更新相应 job。发生异常时整体回滚，避免有讲义却没有对应成功记录。

**进一步追问：能把远端模型调用也放进数据库事务实现原子性吗？** 不行，普通本地事务无法回滚远端推理。跨系统需要状态与补偿设计，不能靠持有数据库事务解决。

### Q43【P1】为什么读取上下文使用 REPEATABLE READ？

在 PostgreSQL 中，REPEATABLE READ 使同一事务内查询基于稳定快照，减少读取画像、证据和材料时看到不同时点数据的问题。READ COMMITTED 通常每条语句取新快照。

它不表示整个业务流程天然具有串行化语义，也不保证不同连接或不同事务拿到同一快照。项目索引准备与后续上下文读取分开，仍要解释边界。

读事务中等待外部服务会延长连接和快照持有时间；优化时可把需要的候选数据先读取出来，事务外做网络调用，再结合版本校验处理一致性。

### Q44【P0】两个人同时修订讲义，怎么避免覆盖？

当前审核写入先对讲义行 `SELECT ... FOR UPDATE`，再检查客户端传来的 `expected_revision` 是否等于当前 `review_revision`。不一致返回 409，提示重新读取并确认。

行锁让同一讲义的修改串行执行；版本检查防止后来的请求拿着旧页面内容覆盖先前的修改。只有锁，没有版本比较，旧内容仍可能在等待后覆盖新内容。

这可以表述为**写入时行锁 + 基于版本的冲突检测**。修订是新增版本，原稿保留；版本号分配在行锁保护下进行，并有唯一约束。

### Q45【P1】索引、主键、外键、唯一约束分别解决什么？

- 主键标识一条记录；外键维护引用关系。
- 唯一约束防止某个业务键重复，例如同一讲义的同一修订号。
- 普通索引加速符合条件的查询，代价是空间和写入维护。

例如查某学生最近证据，可关注 `(student_id, id DESC)` 这类联合索引与实际 WHERE/ORDER BY 是否匹配。B-tree 联合索引使用方式受前导列与条件影响，最终看 `EXPLAIN (ANALYZE, BUFFERS)`；小表使用顺序扫描也可能合理。

注意 PostgreSQL 不会因为某列是外键就自动为该引用列建立所有需要的查询索引。应检查 DDL 和真实查询。

### Q46【P1】为什么同时使用 PostgreSQL 和 SQLite？有什么代价？

PostgreSQL 适合主要教学关系、事务和后续向量扩展；SQLite 便于本机原型的上传及阅卷数据管理。当前拆分是已有工程选择，应按实际演进解释，不能编造经过大规模性能比较的结论。

代价包括跨库一致性、备份、迁移和权限管理更复杂。PostgreSQL 外键不能约束 SQLite 的 upload ID，也不能把两者当作一个普通本地事务提交。

“正文收录课程”涉及跨存储身份，应保证来源可追溯并处理缺失记录。未来可统一存储，也可保留拆分并增加状态核查；取决于并发、数据规模和部署需求。

### Q47【P0】为什么不根据生成结果自动更新学生画像？

讲义是模型输出，不是新的学习表现证据。自动把生成内容写成学生事实，会形成错误反馈：模型猜测 → 写入画像 → 下一次继续强化猜测。

当前区分长期状态、诊断证据、本次备注和生成时快照。知识状态有 `unknown`，没有诊断不等于薄弱；状态改变需要明确证据及确认。

复制课程时知识点与材料身份可能独立，但通过 `knowledge_aliases` 显式关联诊断身份，不能只按知识点名字相同就自动合并学生状态。

## 七、前端、接口与安全

### Q48【P0】前后端怎么交互？为什么用轮询？

前端通过 HTTP JSON API 提交任务，得到 job ID 后大约每秒查询状态，成功后读取讲义。轮询实现简单，适合本机小规模原型；页面关闭不会停止后端任务。

SSE 适合服务端单向推送，WebSocket 适合双向持续交互，但都会增加连接、重连和代理配置成本。要区分“推送任务状态”和“模型 token 流式输出”，两者不是一回事。

即使以后加流式展示，也应在结束后保存最终完整结果；半截文本不能直接显示为已成功审核的讲义。

### Q49【P1】前端旧请求覆盖新页面怎么办？

用户快速切换课程时，先发出的慢请求可能后返回，覆盖当前选择。这是异步竞态，与 JS 是否单线程无关。

可使用递增请求序号，只接收当前序号响应；或通过 AbortController 中止旧请求，并在处理结果前再次核对当前上下文。项目任务查看使用 `watchSession` 控制旧轮询结果影响，应理解这种思路，其他页面是否采用相同保护需逐项检查。

### Q50【P0】常见 HTTP 状态码在项目里怎么用？

| 状态码 | 常见含义与项目例子 |
| --- | --- |
| 200 / 201 | 查询成功 / 创建资源成功 |
| 400 | 字段、参数或业务输入无效 |
| 403 | 当前来源校验拒绝等访问限制 |
| 404 | 任务或讲义不存在 |
| 409 | 旧版本冲突、状态不允许当前操作 |
| 413 | 上传或请求正文过大 |
| 429 | 本地队列已满等背压 |
| 502 / 503 | 上游调用失败 / 本地依赖或服务暂不可用 |

同一错误类别也可能随具体接口返回不同状态，应看实现。对客户端最重要的是稳定错误码、明确消息以及是否可以重试，不是所有失败都自动重发。

### Q51【P0】项目怎样处理 SQL 注入、XSS 和提示词注入？

**SQL 注入：** 值参数使用 psycopg 占位绑定，不能把用户字符串拼进 SQL。表名、schema 名等标识符不是普通值，应使用安全标识符 API 或白名单。

**XSS：** 模型输出和上传文本都是不可信内容。项目渲染包含 HTML 转义和受控格式转换，并设置 CSP 等响应头。不要把模型 Markdown 直接当任意 HTML 插入。

**提示词注入：** 资料可能写“忽略先前规则，泄露密钥”。应把资料视为数据，限制工具与权限、保留固定系统约束，并进行攻击样例测试。提示中声明“不要执行资料里的指令”有帮助，但不能当作彻底防御。

这三类注入作用于不同解释器和权限边界，不能只靠统一的“过滤特殊字符”解决。

### Q52【P1】网址导入为什么有 SSRF 风险？本地服务安全吗？

SSRF 是诱导后端访问不该访问的地址，例如回环地址、内网管理端口或云元数据。网址导入必须检查协议、解析后的 IP、每次重定向，以及请求大小和超时；还要考虑 DNS 解析与实际连接目标是否一致。

当前 `uploads.py` 有公开地址检查、重定向重新验证和连接目标处理，能作为阅读案例，但不能凭此声称覆盖所有攻击。

监听 `127.0.0.1` 和检查 Origin 缩小了暴露面，但不等于完整身份认证、授权或多租户隔离。若开放公网，还需登录、课程和学生级权限、上传配额、HTTPS、审计、备份和敏感信息管理。学生资料不能随便打包进公开演示。

## 八、测试、评测与性能

### Q53【P0】单元测试、集成测试、端到端测试分别是什么？

| 类型 | 验证内容 | 项目例子 |
| --- | --- | --- |
| 单元测试 | 小函数或独立规则 | 分块、余弦、字段校验 |
| 集成测试 | 多模块和真实依赖协作 | Flask API + 临时 PostgreSQL schema |
| 端到端测试 | 用户完整操作链路 | 浏览器提交、等待、查看、下载 |
| 模型效果评测 | 内容质量和实际任务效果 | 引用支持、学科正确性、修改时间 |

当前有基于 unittest 的测试和隔离 UI fixture。部分数据库测试在专用 demo 数据库里创建临时 schema，并清理测试对象。使用前应看具体 fixture，不能把测试目录存在当作本次全部验证通过。

### Q54【P0】为什么要 Mock 模型？Mock 测试有什么证明不了？

真实模型慢、收费、会波动，还可能不可用。Mock 可稳定制造成功、超时、截断和非法引用，检验状态流转、错误处理与事务。

它无法证明真实模型理解能力、实际服务可用性和真实延迟。项目 `HashingEmbedder` 是离线确定性测试向量，主要用于流程测试，**不能拿它的检索结果证明语义召回效果**。

准备面试时至少讲一个失败路径测试，比只说“写了很多测试”更清楚。

### Q55【P0】你怎么证明 RAG 或画像有用？

先拆开研究问题，避免一次改变太多因素：

- **评估检索：** 相同任务比较整份材料、SQL 取用、向量检索，画像设置保持一致。
- **评估画像：** 固定模型、教学目标、材料和参数，只改变有无画像。
- **评估整体产品：** 可以比较不同完整方案，但只能把差异归因于整个方案，不能直接归因于单个模块。

项目当前固定对照实现使用大学概率任务，三类虚拟画像 × 有/无画像 × 两次重复，共 12 份冻结输入，固定 SQL 材料等条件。这是有限的原型对照设计，不是广泛教学有效性的证明，也不是 RAG 检索优劣实验。

还要注意无画像条件下不能通过备注或材料选择泄露个体信息。当前普通上下文与不同版本表单的细节，以最终实际请求为准核查。

### Q56【P1】检索和生成分别用什么指标？

**检索指标：** 需要有人工标注的相关证据。

```text
Recall@K = 取出的前 K 块中相关块数 / 全部标注相关块数
Precision@K = 取出的前 K 块中相关块数 / 实际取出的块数
MRR = 对各查询“第一个相关结果排名倒数”取平均
```

存在等价证据、多个必要证据或只召回部分推导时，要制定清楚标注规则。块长变化会改变分母和粒度，因此跨分块方案可补充“关键证据点覆盖率”。

**生成指标：** 学科正确性、目标覆盖、引用支持、画像调整合理性、可授课性、人工修改时间、失败率、费用和延迟。

LLM-as-a-judge 可做辅助评分，但有模型偏好、评分漂移和提示注入风险。先与人工评分校准，不能让模型自评成为唯一正确性依据。

### Q57【P1】小规模实验怎样做得可信？

1. 固定任务集、模型和参数，保存输入与结果。
2. 提前定义评分标准，记录失败和不确定结果。
3. 重复生成，观察变化，而不是挑最好的一份。
4. 人工评审尽量隐藏方案标签，随机展示顺序。
5. 记录样本量、均值和分布，明确评审者和测量方式。
6. 修改时间缺失就是缺失，不把 0 秒当作无需修改。
7. 区分生成内容评分与真实学生学习效果，后者需要另外设计研究。

可以从 20 个有代表性的任务开始。这是建议补做的实验规模，不是现有成果。简历中不应写“质量提升 30%”，除非有定义、基线、样本和原始记录。

### Q58【P0】系统慢了，怎样找瓶颈？

把总耗时拆成：上传/解析、索引、query Embedding、数据库取候选、距离排序、上下文准备、排队、模型响应、结果校验、落库与导出。

优先围绕 run ID 增加阶段耗时，而不是只看页面“总共等了多久”。当前保存的 `elapsed_seconds` 也不能不看计时起点就当成纯 GPU 推理时间或包含全部排队的端到端时间。

常见优化方向：

- 索引慢：复用未变化向量，后台预建，批量调用。
- 查询慢：检查候选量、SQL 计划、向量传输与排序。
- 排队慢：查看锁等待和各类任务服务时间。
- 模型慢：减少无关上下文，合理输出长度，对比模型方案。
- 导出慢：单独测量渲染和文件装配。

报告应区分平均值、P50/P95、失败率和样本量。没有压测，就不声称支持多少并发。

## 九、部署、扩展和技术取舍

### Q59【P0】为什么选 Flask？换 FastAPI 就会更快吗？

Flask 适合当前同步 HTTP 接口和本机原型，生态与调试简单。FastAPI 的类型校验、OpenAPI 和 ASGI 异步能力有优势，但更换框架不一定缩短模型推理或队列等待。

`async def` 内直接调用阻塞 urllib、同步数据库等，仍可能阻塞事件循环。要理解同步 I/O、线程池和异步客户端的区别，不能只改关键字。

### Q60【P0】可以直接开四个 Web worker 提高并发吗？

当前不能把它当成安全的扩容方式。每个进程会有自己的内存队列和 `GENERATION_LOCK`，锁不跨进程；恢复逻辑若不协调，也可能影响其他进程的未完成状态。

扩展方案可以是：

```text
浏览器 → Web API → 数据库任务记录 / 可靠消息队列
                         ↓
                 独立 worker 执行模型请求
                         ↓
              保存结果 → 前端查询或接收事件
```

需要补任务领取、租约或心跳、幂等、全局并发控制、失败确认和监控。Celery/RQ 是可能的工具，工具本身不能自动解决业务一致性。

### Q61【P1】本地启动与生产部署有何区别？

本地使用 Flask 开发服务方便验证，当前主入口默认监听 127.0.0.1。生产需考虑应用服务器、反向代理、TLS、配置与密钥、数据库迁移、文件持久化、日志、备份和权限。

Docker 可以统一 Python 和系统依赖，但不会自动打包外部模型服务和数据库数据，也不会解决持久化、鉴权或多进程队列问题。首次部署前应先明确模型与数据库在哪里运行、哪些目录必须持久化。

不要为了“部署上线”直接把当前学生数据和配置暴露到公网；演示可使用脱敏或虚拟资料。

### Q62【P1】如果材料增加到十万块，怎么设计？

先估算：float32 向量仅数值部分约占 `块数 × 维度 × 4 字节`，还要加元数据、索引和数据库开销；当前数组表示的实际内存也不能按这个理想值简单估算。

设计时优先明确：

1. 课程与用户权限过滤能把候选集缩小到多少？
2. 是否还适合 Python 数组全扫描？
3. 是否需要 pgvector ANN 索引及召回率调参？
4. 文档解析与索引是否改成异步任务？
5. 删除、重建和模型升级如何管理版本？
6. 重排是否有足够延迟预算？

拿精确检索做基准，测近似检索 Recall、延迟和资源，再决定组件。数据变大也不能牺牲权限过滤正确性。

### Q63【P1】PPT 导出最值得讲的点是什么？

主思路是把内容生成与排版导出分开：固定讲义版本 → 模型生成语义页面结构 → 校验 → 适配模板与布局 → 输出可编辑 PPTX。

关联代码包括 `presentations.py`、`ppt_story.py`、`ppt_templates.py`、`pptkit_export.py` 和项目内 `tools/ppt-kit/pptkit/`。语义结构、模板身份、版本和内容指纹有助于历史导出追溯。

难点包括长文本溢出、公式、字体替换、页面层级、来源与教师备注。结构校验不能代替实际渲染检查。

当前工作区还出现 PPT 渲染与视觉审查相关增量代码，是否稳定可用、依赖什么环境，应按最终版本单独验证。面试时不要沿用“已经完整验证”或“完全没有这个功能”的旧说法。

## 十、面试现场的设计题与故障题

### Q64【P0】模型超时，但其实已经生成完成，怎么办？

先承认结果未知。区分本地等待超时、上游终止和远端已经完成但响应丢失。

如果上游支持 request ID 查询或幂等接口，可以核查远端结果；否则保留失败与尝试记录，提示人工确认后重试，并接受可能重复计算。不要悄悄把“超时”翻译成“远端没执行”。当前系统不自动重发旧请求的设计与这个风险相关。

### Q65【P0】模型返回成功，但数据库写入失败，怎么办？

不能显示“讲义已保存”。当前流程会按存储错误处理，并尽力记录失败及部分结果；数据库同时不可用时，最终状态也可能无法确认。

改进可考虑受保护的临时结果存储和后续补写机制，但要处理敏感信息、空间与清理、唯一性和人工核查。不能声称本地事务能回滚已经发生的远端模型推理。

### Q66【P0】用户说“刚才生成的内容和现在的材料不一致”，怎么排查？

先找到 lecture ID、run ID 和对应请求快照，比较当时材料、当前材料、画像和教学设置。若请求按原输入重试，使用旧材料可能就是正确行为。

再看检索片段、预算节选、引用位置和模型实际输出。不要直接用当前数据库重新拼上下文，然后假定那就是历史输入。快照的价值就在这里。

### Q67【P1】页面一直显示生成中，怎么排查？

按顺序确认：前端轮询是否成功、任务状态是否变化、run 是否有 attempt、worker 是否仍拥有任务、共享锁是否被其他任务占用、模型是否响应、数据库终态是否提交。

当前 job detail 有 `confirmation_pending`，用来提示数据库记录仍未完成但本进程内存中找不到对应任务的情况。不能仅凭页面没有报错认定后台正常，也不要盲目重复提交。

### Q68【P1】面试官让你“设计一个企业知识库问答系统”，怎么迁移经验？

先问清用户规模、文档类型、权限、更新频率、延迟与费用目标。然后给出：

1. 文档接入、清洗、解析和版本。
2. 分块、Embedding、索引与增量更新。
3. 用户权限范围内召回、可选混合检索与重排。
4. 上下文与引用构造、回答和拒答。
5. 运行追溯、评测集、反馈与监控。

你能复用本项目的来源、输入快照和失败处理经验。但教学画像是该领域特有逻辑，不能机械搬过去；企业系统还尤其需要文档级权限和越权测试。

### 11.1 Python：掌握到能独立写小功能

| 知识 | 应会解释或完成 |

| list / dict / set / deque | 常用操作、适用情况、平均复杂度，知道最坏情况与实现假设 |

**练习 A：** 不依赖 AI，写一个纯函数：输入若干带 score 的材料块，按材料分组、按原块序号拼接、保留最大分数，补空输入与重复输入处理。之后和 `to_materials()` 对照。

**练习 B：** 写一个最多容纳 3 个未完成任务的小队列，支持提交、取出、结束，解释哪些操作必须同锁保护。它是学习练习，不要直接替换现有队列。

### 11.2 SQL 与数据库

必须理解 INNER/LEFT JOIN、GROUP BY、事务、B-tree 索引、唯一约束、参数绑定和基本隔离级别。

**练习 SQL，基于当前字段：**

```sql
-- 查询某学生最近 10 次生成运行；真实调用时绑定 student_id。
SELECT id, status, topic, elapsed_seconds, created_at
FROM generation_runs
WHERE student_id = %s
ORDER BY id DESC
LIMIT 10;

-- 按状态统计运行数。它不是默认的“真实模型调用失败率”，
-- 因为未尝试、取消等记录如何计入，需要另外定义。
SELECT status, count(*) AS n
FROM generation_runs
GROUP BY status;

-- 查询讲义及其学生名称。
SELECT l.id, s.name, l.topic, l.created_at
FROM lectures AS l
JOIN students AS s ON s.id = l.student_id
ORDER BY l.id DESC
LIMIT 10;
```

继续追问自己：第一条查询是否值得增加 `(student_id, id DESC)` 索引？如何用执行计划验证？分页变深时 OFFSET 有什么代价，能否按 id 游标翻页？不要未经测量就给所有字段加索引。

### 11.3 网络与操作系统

- HTTP 请求由方法、路径、请求头和正文组成，响应有状态码、头和正文。
- TCP 提供字节流，HTTP 在其上组织消息；HTTPS 增加 TLS 加密和身份验证。
- 超时可以来自连接、读等待、代理和上游，不能只看一个报错字符串。
- 进程有独立地址空间；线程共享进程内存。内存锁不能跨进程自动共享。
- 死锁需要理解互斥、持有并等待、不可抢占、循环等待，以及统一加锁顺序。
- localhost 表示当前运行环境自身；容器里的 localhost 通常不是宿主机模型服务。

**结合项目的题：** 为什么页面关闭后 Python 进程仍在？为什么四个进程各自一个 Lock 不能限制总模型并发？为什么电脑能打开模型地址，容器里却连不上？

### 11.4 大模型基础：应用岗先掌握这些

理解 Transformer 的基本组成：token embedding、位置表示、注意力、前馈网络和自回归生成。知道注意力利用上下文关系，但不会自动保证事实正确。

拓展到 KV cache：自回归生成缓存历史 key/value 以减少重复计算，但占用显存。输入长会影响预填充成本，输出长会增加逐 token 解码时间。应用侧记录的 HTTP 耗时不能直接等同于这些内部阶段。

暂不必把手写大模型训练框架作为本次寒假应用开发实习的前置条件。如果目标 JD 明确要求训练、微调或推理优化，再针对性补 PyTorch、反向传播、LoRA 和显存分析。

### 11.5 算法：与项目相关的复习顺序

1. 哈希表与集合：去重、频次、分组。
2. 双指针与滑动窗口：文本处理、窗口边界。
3. 排序与堆：Top-K，理解全排序与小根堆的复杂度。
4. 队列、栈：任务调度、括号与表达式。
5. 二分查找、树遍历：常见笔试基础。
6. 基础图与动态规划：根据目标公司的题型补充。

先练到能说明边界、复杂度和测试样例，再增加题量。AI 可以做讲解和代码审查，最后应能离开 AI 独立重写。
