# 规模数据与评测基线

预置数据很小：6 名学生、6 个知识点、6 段材料。材料最长的一段也短于向量检索的分块长度（500 字符），每门课只有 3 个片段，而向量检索取前 6 段——结果必然与「全部关联材料」完全相同，检索对比没有意义；16000 字符的材料预算也从未触发。`demo/scale/` 用来补上这一块，全部是可选的，不运行就不影响现有数据。

## 内容

| 文件 | 作用 |
| --- | --- |
| `corpus/linear_equations.json`、`corpus/conditional_probability.json` | 两门整章课程，各 12 个知识点。每个知识点有一段自编讲解（概念、依据、常见错误）和 2 条带标注的教学问题 |
| `examples.py` | 按知识点类型生成例题与检验。所有数字用精确分数计算，同一随机种子输出相同文本 |
| `load.py` | 把语料装进数据库并生成合成班级；`--remove` 删除它创建的数据 |
| `eval_retrieval.py` | 检索评测，不需要数据库 |
| `bench.py` | 生成基准（旧的分章节和单次写作方式），在一次性的隔离库里运行 |
| `evalset.json`、`evalset.py` | 默认写作方式（课堂设计）的固定评测集，12 节课分 dev 和 holdout；在一次性的隔离库里运行 |
| `design_compare.py` | 用课堂设计方式重写数据库里已保存的讲义，与原稿比较（只读数据库） |

语料是自行编写的讲解加程序计算的例题，不是教材原文；主题参照预置材料所用的 OpenStax 章节范围。讲解中的数字例子（如基础率示例）均为假设。

## 装载与清除

```bash
.venv/bin/python demo/scale/load.py                          # 两门课 + 每门课 40 名合成学生
.venv/bin/python demo/scale/load.py --students 12 --examples 4
.venv/bin/python demo/scale/load.py --remove
```

- 装载后在「讲义工作台」的备课副本里会多出「一元一次方程整章（扩展语料）」和「条件概率与贝叶斯整章（扩展语料）」。默认每个知识点 8 道例题，两门课约 1.4 万和 2.4 万字符。
- 合成学生的副标题以「合成·」开头。每人按能力层次（基础待巩固 / 常规 / 学有余力）和知识点在章节中的位置抽样出掌握状态，约 15% 的知识点没有证据（保持「未知」）。证据通过与教师逐条录入相同的确认路径写入，记录者为「合成数据脚本」。这些状态是抽样得到的，不是观察结果。
- 重复运行不会重复装载。`--remove` 只删除带标记的数据；已经有讲义、生成记录或题组的合成学生会保留并列出，因为这些记录引用了他们。
- 自建备课副本对全部学生可用，所以合成学生也会出现在其他备课副本的学生列表里。

## 检索评测

```bash
.venv/bin/python demo/scale/eval_retrieval.py                  # 离线，哈希向量
.venv/bin/python demo/scale/eval_retrieval.py --embedder qwen  # 已配置的嵌入模型（真实调用，约 400 段文本）
```

对每门课，把整章的全部片段按每条问题排序，命中指排在前 k 的片段里有属于该问题所在知识点的片段。比较三种排序：应用现在使用的向量余弦、字符二元组 BM25、两者的倒数排名融合。输出 recall@1/3/6、MRR 和前 6 段中命中片段的比例。

离线哈希向量只反映字面重合，那一行不能说明语义检索的效果；它的用处是让脚本不联网也能跑通，并给 BM25 一个参照。要评价真实的嵌入模型请加 `--embedder qwen`。

注意应用里的向量检索只在所选知识点内排序，这里是在整章范围内排序，题目更难，用来回答「如果以后改成按章节检索，够不够用」。

### 结果（2026-11-17）

真实嵌入模型为 `text-embedding-v4`（阿里云百炼），一次运行嵌入 113 个片段和 48 条问题，共 161 段文本，用时约 12 秒。离线哈希向量一行只作参照。

| 课程 | 排序方法 | recall@1 | recall@3 | recall@6 | MRR |
| --- | --- | ---: | ---: | ---: | ---: |
| 一元一次方程（40 个片段） | 向量 · text-embedding-v4 | 0.792 | 0.917 | 0.958 | 0.867 |
| | BM25 | 0.792 | 0.958 | 0.958 | 0.873 |
| | 融合 · text-embedding-v4 + BM25 | **0.875** | **1.000** | **1.000** | **0.931** |
| | 向量 · 离线哈希（参照） | 0.583 | 0.750 | 0.833 | 0.706 |
| 条件概率与贝叶斯（73 个片段） | 向量 · text-embedding-v4 | 0.708 | **0.958** | **0.958** | 0.832 |
| | BM25 | 0.458 | 0.833 | 0.958 | 0.661 |
| | 融合 · text-embedding-v4 + BM25 | **0.792** | **0.958** | **0.958** | **0.880** |
| | 向量 · 离线哈希（参照） | 0.292 | 0.625 | 0.833 | 0.501 |

- 真实嵌入模型在整章范围内把正确知识点的片段排进前 3 的比例为 92% 和 96%。概率一章术语相近（条件概率、全概率、贝叶斯），字面匹配的 BM25 明显变差，向量检索的优势在这一章。
- 两者融合在两章都最好，但应用目前只实现了向量排序。
- 每门课只有 24 条问题，一条问题相当于 4 个百分点；问题和讲解都是自编的，与教师上传的教材片段会有差距。

据此的决定写在 [features.md 的「材料取用方式与检索」](features.md#材料取用方式与检索)：向量检索保留为可选项，默认仍是精确 SQL。

## 生成基准

```bash
.venv/bin/python demo/scale/bench.py                                   # 模拟模型，12 份讲义，并发 1 与 3
.venv/bin/python demo/scale/bench.py --jobs 40 --latency 8 --concurrency 1 3 6
.venv/bin/python demo/scale/bench.py --real --jobs 2 --concurrency 3  # 真实模型，会产生费用
```

脚本像测试一样在专用数据库里建一个临时 schema，装入扩展语料和合成班级，通过真实的批量接口、队列、并发闸门和存储代码生成讲义，结束后删除这个 schema。

- **模拟模式**只替换模型调用：等待 `--latency` 秒后返回一份达到篇幅要求的回复。它衡量的是流水线本身（排队、并行写章节、检查、保存），不反映模型质量。
- **`--real`** 不替换模型调用，并额外统计每份讲义的汉字数、篇幅检查通过率、各项程序检查的提示次数和平均 token 用量；讲义和结果保存在 `.runtime/bench/<时间>/`。

本机一次模拟运行的结果（条件概率整章，材料 24469 字符，6 份讲义，每次调用 0.5 秒）：并发 1 用时 18.4 秒，并发 3 用时 6.3 秒，快 2.9 倍；每份讲义的输入约 3.6 万字符。

`bench.py` 只测旧的写作方式（`--mode sectioned-v1` 或 `single`）。2026-11-10 用真实模型跑过两次分章节写作，各 2 份讲义：第一次 2 份都因模型输出达到长度上限而失败；第二次 2 份都保存了，5816 和 5554 个汉字，篇幅检查都没通过，平均每份约 15.8 万 tokens、6—7 次模型调用、135—169 秒。默认的课堂设计方式用下面的评测集测。

## 评测集（默认写作方式）

```bash
.venv/bin/python demo/scale/evalset.py                                  # 预演 dev 的 8 节：只建课、统计请求大小，不调用模型
.venv/bin/python demo/scale/evalset.py --cases L1 L2 P1 P2 --real       # 真实模型，会产生费用
.venv/bin/python demo/scale/evalset.py --cases L1 L3 P1 P3 --modes profile none --real   # 同一节课有、无画像各一份
```

`evalset.json` 是 12 节固定的课，用上面两门扩展语料，每节 2—3 个知识点：

| 分组 | 课 | 覆盖 |
| --- | --- | --- |
| `dev`（8 节） | L1—L4、P1—P4 | 两门课；个人 4 节、全班 4 节；40、45、90 分钟 |
| `holdout`（4 节） | L5、L6、P5、P6 | 同上，知识点与 dev 不重叠 |

**规矩**：调提示词和程序检查只看 `dev`。`holdout` 只在发版前跑，不对着它改；对着它改过，它就不再是留出的课。每次改 `design.py`、`designed.py` 或 `prompts/lecture-design-*.md` 后，至少重跑 `dev` 里的同一组课再对比。

脚本像 `bench.py` 一样在专用数据库里建临时 schema，结束后删除。它装入扩展语料和合成学生，按服务启动时的做法把语料归到课程下（`classes.ensure_course_structure`），每门课建一个「评测班」并把学生加进去；之后走页面的接口：每节课用 `/api/course-tasks` 保存备课（从课程知识点库勾选知识点），再按页面提交的格式交给 `/api/jobs`（课堂设计、`rich-v1`、不停下来等教师确认）。个人课选该能力层次的第一名合成学生，全班课用班级画像。合成学生资料里标记用的句子（「合成学生，用于规模测试……」和副标题的「合成·」）在临时 schema 里去掉，模型读到的就像教师写的记录。

- **预演**（不加 `--real`）建好全部课，打印每节课堂设计请求的系统提示和输入字符数、材料条数和提示词版本，不调用模型。
- **`--real`** 先按已测用量估计 tokens（45 分钟一节约 8.5 万，按时长折算）；估计超过 60 万时要加 `--yes` 才运行。
- **`--modes profile none`** 每节课各生成有画像和无画像两份（全班课是班级画像和无画像），另在 `blind/` 里输出盲评材料：每对讲义随机命名为 A、B，对应关系存在 `key.json`，`评分表.md` 用 `quality_baseline.py --sheet` 的六个维度。评分时不要打开 `key.json`。有画像的讲义会写到学生的情况，评分者多半看得出哪份是有画像的，这是这种对照本身的局限。

结果写在 `.runtime/evalset/<时间>/`（不进仓库）：每节的讲义、课堂设计 JSON 和各阶段记录，`results.json`，以及 `summary.md`。`summary.md` 每节一行：tokens、秒、模型调用次数、课堂设计是否重试、重写的环节、最终仍有的提醒（按类别）、程序检查未通过的项目、汉字数；表尾给中位数、重试率，以及第一次设计的问题、重写原因、最终提醒各按类别出现在几节课里。类别按提醒的措辞归类（`evalset.CATEGORIES`），检查改了措辞就要跟着改。

学科：课程有「学科」一项（2026-11-18 起，F1）。评测集按 `evalset.json` 的 `subjects` 把一元一次方程的课程设为数学、条件概率的课程设为概率统计，提示词版本因此带 `+math-general-v1` 或 `+probability-general-v1`；加 `--no-subject` 则两门课都按「其他」建，与 11-17 的第一次运行相同。

- **L2 失败的原因是程序检查，不是模型**：模型在板书列表里用空字符串 `""` 隔开三道例题，`design._Reader.lines` 把空的一行当成「缺少内容」的结构错误，重试一次后整节课失败（报错文字为「环节 S3的板书（board）缺少item」）。当时失败的生成记录不保存用量和阶段记录，所以这节两次课堂设计调用的用量没有计入。两处都已于 2026-11-18 修好：空项直接去掉；失败的记录也保存用量和各阶段的问题，评测集的 `summary.md` 对失败的课同样列出 tokens 和设计是否重试。

- **「目标与检验题」提醒列出的「词」常常不是词**：例如「出等」「入数」「对后」，是从目标里拆出的两个字。模型照着这样的提醒改不出来，L1 重试后还剩 9 条。
